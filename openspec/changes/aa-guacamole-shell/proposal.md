# Phase AA - Guacamole shell: a second binary that embeds the server and shows placed figures on the TV

## Why

Guacamole needs a body before it can grow organs. Every later rung (intros, turntables, levels) assumes a Bevy app that owns the TV, embeds the SAME Axum server and phone SPA the product runs and gets portal events with no emulator and no figure file underneath. None of that exists: the server's bootstrap lives in the product's `main.rs`, the only drivers behind `PortalDriver` are RPCS3-shaped (IPC, UIA) or the in-memory mock, and the phone's figure list is whatever the firmware pack holds. AA builds that body on the full reset (`docs/native/guacamole-design.md`, Figures): a figure is an identity, and guacamole reads no `.sky` and needs no firmware pack, RPCS3 install or product setup. It ends on something the kids can see: place a figure on the phone, its card shows up on the TV, in `guacamole`.

## What Changes

- `crates/server` splits in two without changing the product's behavior, and only what guacamole runs moves (chotchki, 2026-10-17: "I'm good with it").
  - The Axum router, phone SPA serving, the profile store, the driver worker, watchdogs, mDNS, QR, paths and logging move into a new library crate both binaries link.
  - `.sky` editing and stats, working copies, the display-mode and RPCS3-config helpers, the product's config loader and wizard, its migrations and the eframe launcher (`ui/`, the badge and vortex rigs, the GL fallback, the macOS compositor) stay in `crates/server` and leave with it at G1. Where moved code calls one of them, the product hands it to the boot call as a hook and guacamole hands none. The product keeps its Windows resource stamping, and its release plumbing (`-p skylander-server` in `release.yml`, the WiX metadata, the e2e harness) keeps working unchanged.
  - The bootstrap (`crates/server/src/main.rs:67-645`: pack indexing, bind address, phone URL, QR, the tokio thread, DB, worker, watchdogs, catalogue, router) becomes one library call. The driver is built by a factory that runs ON the tokio thread, because the UIA driver initializes COM there (`main.rs:259-262`).
  - The listener binds BEFORE the profile database opens, so whichever binary starts second fails on the port without opening its database.
- A new driver kind, Native, for "no emulator and no figure file underneath". Every branch keyed on RPCS3 or on a figure file gets an explicit arm (where the code behind it stays in `crates/server`, the arm is the missing hook), since some of them do real damage without one:
  - `BootDirect`'s non-IPC arm spawns RPCS3 through UIA on Windows for ANY driver that has no IPC socket (`crates/server/src/state.rs:1564`, `:1685`), so a native driver on the HTPC would try to launch the emulator.
  - `/api/launch` pre-sets the Windows display mode saved for the game and captures it again after the first figure loads (`http.rs:1158`, `:1323`). Under guacamole that would save the desktop mode as Giants' preferred mode and the product would apply it on its next Giants boot.
  - The window-mode and 2× admin toggles rewrite the controller's `config.json` (`http.rs:948`, `:998`) and RPCS3 settings opens the emulator (`http.rs:1629`). Under Native all three answer 409, the way settings already does for Mock.
  - Every load, slot reset, Kaos swap and auto-restart restore forks or rewrites the profile's `.sky` working copy (`http.rs:661`, `:773`, `state.rs:480`, `:1021`). Under Native none of them touches a file: a placement carries the figure's identity and the profile that placed it.
  - The figure stats, edit and reset routes (`http.rs:285-299`) answer 409 under guacamole, which hands the boot call no figure-file hook. `sky_stats` and `sky_edit` stay in `crates/server`, so `crates/sky-parser` isn't in guacamole's dependency tree at all.
  - No RPCS3 Net-config write at startup (`main.rs:341`), no EBOOT resolution (`http.rs:1191`) and no `games.yml` read.
- An interim figure catalogue, because without the pack there's no figure list. Today the indexer (`crates/indexer`) walks the pack: a figure's name comes from its dump's file name, its game, element and category from the folder it sits in and its id from the dump's tag header. `data/figures.json` isn't read at runtime by anything (only `tools/wiki-scrape` and `tools/rekey-figure-ids` touch it). Portraits are `data/images/<figure id>/thumb.png`, keyed by the same tag-form id `<toy type>-<variant>`. guacamole builds its catalogue at boot from those two, cut to what Giants plays, with a validation pass because the wiki data is measurably patchy and partly mis-keyed (design decision 5). The same list goes to every profile. It's interim: AB's extracted roster is the groundwork and AE replaces it with names, elements and portraits from the disc.
- Guacamole's own setup, one question: where the disc dumps are. Release asks on the TV the first time (a native folder picker on the PC) and dev reads `GUAC_DUMP_DIRS` from `.env.dev`. guacamole scans the chosen folders for `PS3_GAME/PARAM.SFO`, reads each title id with AB.2's parser and offers Giants when a BLUS30968 dump is there. It needs no RPCS3 path, PS3 firmware, figure pack, `games.yml` or product wizard.
- Guacamole's own data, from AA on (chotchki, 2026-10-17): its own SQLite under its own data root (`%LOCALAPPDATA%\guacamole\` in release) holds its profiles, PINs and settings (the dumps folders, its port, its pairing key), with a migration set of its own. Profiles aren't copied from the controller: "set them up again, it's super simple", so the first phone to join creates one through the phone's existing create-profile flow. guacamole never opens the controller's `db.sqlite` or `config.json`. It binds the same default port (8765) and mDNS name, so the join address doesn't change, but with its own pairing key a phone that last joined the controller gets the phone's existing pairing screen and scans guacamole's join code once (design decision 6).
- `NativePortalDriver` implements the existing trait (`crates/rpcs3-control/src/lib.rs:23`) and places by identity: the figure's id (toy type + variant), name, element, portrait and owner (the placing profile's colour and initial) go to the Bevy world over a channel, and `clear` sends the removal. How the trait carries a placement without a file is design decision 4. `open_dialog` (required) is a no-op and the IPC-only methods keep the trait's "not applicable" defaults, like `MockPortalDriver` (`crates/rpcs3-control/src/mock.rs:92`). Trimming the trait waits for G1.
- `guacamole`, a new Bevy 0.20 binary (`crates/guacamole`). It boots the shared server with the native driver on a background tokio thread and owns the main thread and the TV window. The TV shows setup on the first run, the join QR, then after a game is picked one card per occupied slot: portrait, name, element and an owner pip. No level, XP or gold: every figure is fresh until guacamole keeps its own progression (AH), so there's nothing to show. SHUT DOWN on the phone closes it, back to Steam Big Picture.
- The phone enables its STATS (level and gold) and RESET TO FRESH actions only when the figure's stats came back. Under guacamole they never do, so both stay disabled with a "not available yet" note until AH puts them on guacamole's own store. Under the product, stats come back whenever an edit could work, so it behaves as before.
- The e2e harness runs the existing phone suite against either binary, and the test-only failure injection works with the native driver too. A guacamole-only test reads back what the TV shows through a test hook. The tests that need a figure file stay product-only.

## Capabilities

### New Capabilities

- `guacamole/shell`: how the guacamole app gets set up and coexists with the product on one machine. Setup that asks only for the disc dumps, profiles and PINs of its own that the kids set up again, the same join address with a pairing of its own, one app at a time, Giants as the only game, the controller's profiles, settings and figure files left alone, shutting down from the phone.
- `guacamole/figure-cards`: what the phone offers and the guacamole TV shows. The whole Giants figure list for every profile, the join code, a card per figure on the portal with its identity and owner, how placements, removals, swaps and failures change it and figure progress not shown or edited yet.

### Modified Capabilities

None. `openspec/specs/` is empty; these are the track's first specs.

## Impact

- Track: Guacamole, the first rung of the ladder. Disc serial read: BLUS30968, and only its `PS3_GAME/PARAM.SFO` (setup reads the SFO of each dump in the chosen folders to find it); nothing under USRDIR. guac-extract's output doesn't exist yet, so no extract layout or IR version is involved.
- Kid-visible milestone: a phone placement shows up on the TV as a card with the figure's portrait, name, element and the placing kid's pip, in guacamole, on the HTPC under Steam Big Picture.
- Code:
  - New crate `crates/guac-server` (package `guac-server`). It takes what guacamole runs: `embedded_assets`, `http`, `kaos`, `logging`, `mdns`, `paths`, `profiles`, `round_qr`, `state`, the config types both loaders fill and the `BUILD_TOKEN` half of `build.rs`, plus a new `migrations/` set for guacamole's own database (the product's profile tables, same shape, and a settings table).
  - `crates/server` keeps `sky_edit`, `sky_stats`, `working_copies`, `display_mode`, `rpcs3_config`, its `config` loader, the wizard and its `PersistedConfig`, its own `migrations/` (frozen at three) and the eframe modules, behind hook traits the moved code calls. `sky-stats` stays a feature of `crates/server` the product enables as it does today. `main.rs` shrinks to GL bootstrap, config, logging, boot and eframe. AD (the ACR122 removal) lands before AA, so `nfc`, `nfc-import` and the `scan:` arms are already gone and the split has none to leave behind.
  - `gl_fallback::APP_DIR_ENV` moves into `paths`.
  - New crate `crates/guacamole`. `crates/rpcs3-control` gains the defaulted `place` method and the test-hook injector trait, nothing else.
  - `phone/`: the STATS and RESET TO FRESH gate.
  - `data/figures.json` and `data/images/` are read, not changed.
- Dependencies: `bevy` 0.20.0 (MSRV 1.97.1, local toolchain 1.99.0) and a native folder-dialog crate (AA.5 picks; `rfd` is the first candidate) in `crates/guacamole` only. No `bevy_egui`. `guac-formats` for the PARAM.SFO reader, so AA.5 lands after AB.2.
- Tests: the product's phone e2e suite (`crates/e2e-tests`) gates the split. It must pass unchanged against the product, with the pass count it had before AA.1, then again against guacamole minus the tests that need a figure file. The HTPC live smoke (the product boots Giants over IPC and loads a figure) proves the split didn't move the product, and because a tagged MSI installs this source's product on the HTPC, AA.13 repeats that check from the installed MSI, profiles and figure progress included.
- CI and the pre-push hook: `cargo clippy/build/test --workspace` now compiles Bevy on the Windows CI lane and in `.githooks/pre-push` on the Mac. The macOS CI lane has been disabled (`if: false`) since 2026-05-30, so nothing in CI builds guacamole for macOS; the `fmt` job on Ubuntu doesn't compile, so Bevy's Linux system libraries (ALSA, udev) are never needed. AA.10 measures what Bevy adds to both.
- Owning doc: `docs/native/guacamole-design.md` (Architecture "Two binaries until G1", Persistence and setup, Figures). CLAUDE.md's Architecture, Data & paths and Dev-mode sections move with it, because the workspace layout, the runtime roots and the "one binary" picture change.
- Release reach: the Windows MSI carries both binaries, the starting point for distribution (chotchki, 2026-10-17: "Eventually this will be MSI based, this is where dual binaries is a good starting point"). A `v*` tag, only on chotchki's word (AA.13), publishes it; installing it on the HTPC upgrades the frozen controller in place to the product built from this source, beside guacamole. So AA.1 and AA.2 change the product's source and must not change its behavior, and the Tests line above is how that's held. The phone gate reaches the product's phone with that release, where it changes nothing (stats come back whenever an edit could work). The dmg stays product-only (guacamole runs from `cargo` on the Mac).
- One-way doors: none new. guacamole's database is its own file under its own data root with a migration set of its own, and guacamole never opens the controller's `db.sqlite` or `config.json`, so nothing it adds (now or at AH) reaches the controller's data. Deleting guacamole's data root takes it back to first run.
